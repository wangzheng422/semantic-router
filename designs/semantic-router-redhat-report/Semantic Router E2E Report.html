Executive frame

本次实验回答六个运维问题

汇报重点不是算法论文，而是客户能否部署、验证、解释、清理并复现实验。

01
环境能否恢复

GPU VM 重启后，工作目录、Podman 网络、模型容器和路由栈能否恢复。

02
双模型能否共存

Qwen 3.5 2B 和 27B FP8 同时提供 OpenAI-compatible API。

03
请求如何分流

从固定小模型、关键词，到 hybrid 成本质量权衡逐步验证。

04
多轮是否动态切换

主题从账号请求切到分布式事故后，路由能否切到 27B FP8。

05
缓存是否降低成本

重复请求命中 semantic-cache 后，不再访问后端模型。

06
客户如何验收

用响应头、模型列表、端口和 dashboard 健康检查形成签收标准。

端到端链路由五层组成

Envoy 接收 OpenAI 请求，semantic-router 做语义判断，vLLM 后端负责最终生成。

Client side
客户应用OpenAI SDK / Chat API
请求数据model, messages, headers, max_tokens
验收信号x-vsr-selected-model, cache-hit, matched signals
Routing plane
Envoy8888 OpenAI API + ext_proc
semantic-routersignals, decisions, model selection, plugins
Dashboardconfig, models, status, metrics
Model plane
qwen35-2b低成本、简单请求、短摘要
qwen35-27b-fp8复杂推理、多轮、事故分析
持久缓存模型缓存和 router 本地模型位于 /var/mnt

Scenario 2

场景二用关键词建立第一层分流

关键词是最容易解释的入口规则，适合作为客户第一组业务分流实验。

简单请求

shortone sentence
命中 explicit_simple，通常走 2B。

复杂请求

incidentroot cause
命中 explicit_complex，进入复杂 decision。

阈值解释

bm25_threshold: 0.05 适合 PoC；生产应基于真实日志回放调参。

请求预期响应头通过标准
短摘要x-vsr-matched-keywords: explicit_simple选中 qwen35-2b
生产事故x-vsr-matched-keywords: explicit_complex进入复杂 decision

Model cards

场景三用模型卡片解释选择依据

模型卡片把“模型能力、成本、质量”写进配置，让路由选择能够被运维解释。

模型能力标签质量分成本定位
qwen35-2bchat, fast-response, account-support, concise-summary0.62低成本基线
qwen35-27b-fp8reasoning, code, technical-support, security, incident-analysis0.91高成本高质量
运维可调

价格、quality_score、capabilities 都是治理入口。客户可以按内部成本和质量评测结果修正。

路由可解释

响应头告诉你选了哪个模型；模型卡片告诉你这个选择背后的能力和成本假设。

Production caveats

生产化需要补齐治理和边界验证

PoC 已证明主链路和关键场景；生产前还要处理数据、版本和成本边界。

风险当前观察生产建议
replay API本轮 runtime 中 router_replay API 返回 404目标版本上线前重新验证 replay/dashboard API
缓存错配semantic-cache 阈值设为 0.995基于真实问答回放评估阈值
成本策略hybrid 会因 cost_weight 压制 27B用真实成本和质量评测调整权重
审计数据请求体可能包含敏感内容开启脱敏、保留周期和访问控制
